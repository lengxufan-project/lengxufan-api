# 架构决策记录

> 记录冷旭帆项目从 v1.0 到 v5.5 的关键架构决策及其原因。

## 1. 为什么是混合架构（规则引擎 + 大模型）？

**决策时间**：2026年4月19日

纯大模型方案无法精确控制角色的情绪值和行为边界。纯规则引擎方案无法生成自然语言。
混合架构让代码精确管理"里子"（情绪值、状态标签、记忆），大模型负责"面子"（自然语言生成）。

## 2. 为什么是30文件模块化架构？

**决策时间**：2026年7月19日

从单文件（400行）重构为30文件。核心原则：**一个文件只做一件事，数据与逻辑分离**。
`character_data/` 下的文件全是纯数据（Python 字典/列表），不含任何函数或类。
改角色设定只需改数据文件，不动逻辑代码。

## 3. 为什么是四阶段认知处理链？

**决策时间**：2026年8月2日

冷旭帆的回复不是"用户输入 → AI 输出"，而是经过四个阶段：
1. 场景感知 → 他现在在哪、周围有谁、什么时间
2. 上下文分析 → 用户在问什么、什么意图、什么情绪
3. 信任验证 → 这个人是谁、能不能信
4. 生成输出 → 动作 + 台词 + 心理独白

这个架构让每个阶段可以独立测试、独立优化。

## 4. 为什么前后端分离？

**决策时间**：2026年8月4日

`run.py` 从 250 行膨胀到无法维护。前端 HTML/CSS/JS 混在一个文件里。
分离后：`routes/` 只处理 HTTP 请求，`services/` 负责业务逻辑，
`frontend/` 是独立静态项目。加新角色、换前端框架，后端 API 一行不改。

## 5. 为什么是角色注册中心？

**决策时间**：2026年8月4日

做黄景云时发现：复制冷旭帆的整个 `character_data/` 目录太笨重。
角色注册中心让每个角色 = 一个独立目录（`characters/角色名/data/`），
引擎启动时自动扫描加载。加新角色只需要写数据文件，不需要改任何引擎代码。

## 6. 为什么是 SQLite 而不是 MySQL/PostgreSQL？

**决策时间**：2026年8月3日

- SQLite 是一个文件，不需要额外安装数据库服务
- 腾讯云服务器 2核2G，MySQL 会额外消耗 200MB+ 内存
- 单用户场景下 SQLite 性能完全足够
- 将来迁移只需改一行配置（SQLAlchemy 语法完全一样）

## 7. 为什么用户状态需要双向感知？

**决策时间**：2026年8月4日（P1 深化）

之前冷旭帆只知道自己"情绪低落"，不知道用户"很开心"。
双向感知让用户情绪直接影响冷旭帆的情绪值（用户开心→冷旭帆+3，用户悲伤→冷旭帆-3）。
同时追踪用户的话题偏好（常提草莓/糖/方言），让回复更有针对性。
